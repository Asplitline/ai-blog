> 这是一次真实上线的复盘。目标有三个：看完知道**整体流程**，知道**哪里会踩坑**，以及能**照着清单一步步做完**。
>
> 文中的 IP、域名、账号、实例 ID、端口入口等都已脱敏，用 `<ECS_IP>`、`app.example.com` 这类占位符代替。

## 背景和最终架构

应用是一个典型的 Bun 全栈 monorepo：

```text
apps/server   Bun + Hono 后端，SQLite 存数据，顺带托管前端静态文件
apps/web      React + Vite 前端，构建产物是一堆带 hash 的静态文件
```

服务器是一台 2 核 2G 的阿里云 ECS（大陆地域），上面已经跑着 1Panel 和它自带的 OpenResty，80/443 被占用。域名 DNS 托管在 Cloudflare。

最终上线后的样子：

```text
浏览器
  │  https://app.example.com
  ▼
Cloudflare DNS（仅 DNS，灰云，直接解析到 ECS）
  ▼
ECS : 443  ── 1Panel OpenResty（证书 + 反向代理）
  │            proxy_pass http://127.0.0.1:3000
  ▼
Docker 容器 app（Bun 后端，只监听 127.0.0.1:3000）
  ├── /data         ← 宿主机 ./data         SQLite 数据库、备份
  └── /web          ← 宿主机 ./web（只读）   前端版本目录
        ├── releases/<版本1>/
        ├── releases/<版本2>/
        └── current -> releases/<版本2>    后端从这里托管前端
```

几个关键设计：

- **镜像只装后端**。前端不进镜像，单独上传到宿主机，通过 volume 挂进容器。
- **前端发布 = 上传新目录 + 切软链**，不用重启后端。
- **镜像放在阿里云 ACR 个人版**（免费），本机推公网地址，ECS 走 VPC 内网地址拉取。
- **一套脚本同时给本机和 CI 用**，配置从文件或环境变量读。

## 整体流程

```text
一次性准备
  ├─ ① 摸清服务器：架构、内存、端口占用、已有的 Web 服务
  ├─ ② 开通 ACR 个人版 → 建命名空间 → 设固定密码
  ├─ ③ ECS：免密 SSH、装 Docker、docker login（VPC 地址）
  ├─ ④ 本机：填部署配置、docker login（公网地址）
  ├─ ⑤ 初始化：上传 compose / 备份脚本 / .env 模板，改服务器 .env
  ├─ ⑥ 首次发布：先后端，再前端
  ├─ ⑦ 创建账号
  └─ ⑧ 域名 + HTTPS：DNS 记录 → 反向代理站点 → 证书 → 安全 Cookie → 关临时入口

日常发布
  ├─ bun run deploy:server   只发后端（测试 → 构建镜像 → 推送 → 服务器拉取重启 → 健康检查）
  ├─ bun run deploy:web      只发前端（类型检查 → 构建 → 上传 → 切软链 → 检查入口 JS）
  └─ bun run deploy          两个都发，先后端再前端
```

## 一次性准备：按步骤操作

每一步都带「验证」，验证通过再往下走。

### ① 摸清服务器（只看不改）

```bash
ssh root@<ECS_IP> 'uname -m; free -h; df -h /; docker --version; docker compose version'
ssh root@<ECS_IP> "ss -ltnp | grep -E ':(80|443|3000|8443) '"
ssh root@<ECS_IP> 'docker ps --format "{{.Names}}\t{{.Image}}\t{{.Ports}}"'
```

要回答的问题：

| 问题 | 影响什么 |
|---|---|
| `x86_64` 还是 `aarch64` | 构建镜像的 `--platform` |
| 80/443 被谁占了 | 用系统 Nginx 还是 1Panel 的 OpenResty 做反向代理 |
| 3000 端口是否空闲 | 应用对宿主机暴露的端口 |
| 可用内存、有没有 swap | 小机器上多跑一个服务是否吃紧 |

**验证**：上面每个问题都有答案。

### ② 开通阿里云 ACR 个人版

1. 控制台 → 容器镜像服务 → 个人实例 → 创建个人版，**地域和 ECS 一致**。
2. 新建命名空间，类型选「私有」，打开「自动创建仓库」（第一次推送时自动建仓库）。
3. 访问凭证 → 设置固定密码。
4. 记下「登录实例」里给出的**专属域名**和用户名（就是阿里云账号名）。

新开的个人版实例域名长这样（见坑 6）：

```text
公网：crpi-<实例ID>.<region>.personal.cr.aliyuncs.com       本机推送用
内网：crpi-<实例ID>-vpc.<region>.personal.cr.aliyuncs.com   ECS 拉取用
```

**验证**：命名空间列表里能看到新建的空间，权限是「私有」。

### ③ 准备 ECS

```bash
# 免密登录：第一次需要输 ECS 的 root 密码（不是阿里云账号密码）
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@<ECS_IP>

# 服务器登录 ACR 的内网地址，密码是 ACR 的固定密码
ssh -t root@<ECS_IP> "docker login --username=<阿里云账号名> crpi-<实例ID>-vpc.<region>.personal.cr.aliyuncs.com"
```

没装 Docker 的话：`curl -fsSL https://get.docker.com | sh -s -- --mirror Aliyun`。

忘了 root 密码有两个办法：控制台「重置密码」（要重启实例），或者用 Workbench 免密连上去，手动把公钥追加到 `~/.ssh/authorized_keys`（不用重启）。

**验证**：`ssh -o BatchMode=yes root@<ECS_IP> true` 不要密码就能退出；服务器上的 `~/.docker/config.json` 里有 `-vpc` 那个域名。

### ④ 准备本机

```bash
docker login --username=<阿里云账号名> crpi-<实例ID>.<region>.personal.cr.aliyuncs.com
cp deploy/.deploy.env.example deploy/.deploy.env
```

`deploy/.deploy.env`（已加进 `.gitignore`）：

```bash
ACR_REGISTRY=crpi-<实例ID>.<region>.personal.cr.aliyuncs.com
ACR_NAMESPACE=<命名空间>
ECS_HOST=<ECS_IP>
ECS_USER=root
ECS_DIR=/opt/my-app
APP_PORT=3000
PLATFORM=linux/amd64
```

**验证**：`git status` 里看不到 `deploy/.deploy.env`。

### ⑤ 初始化服务器目录

```bash
bun run deploy -- --init
```

它会跑测试、构建并推送一次镜像，然后把 `docker-compose.yml`、备份脚本、`.env` 模板传到 `ECS_DIR`。接着改服务器上的 `.env`：

```bash
IMAGE=crpi-<实例ID>-vpc.<region>.personal.cr.aliyuncs.com/<命名空间>/my-app:latest
APP_PORT=3000
COOKIE_SECURE=false   # 先 HTTP 验证时必须是 false，上了 HTTPS 再改 true
```

compose 里和前端分离发布相关的两处：

```yaml
services:
  app:
    image: ${IMAGE}
    env_file: .env
    environment:
      WEB_DIST_DIR: /web/current
    ports:
      - "127.0.0.1:${APP_PORT:-3000}:3000"   # 只监听本机，交给反向代理
    volumes:
      - ./data:/data
      - ./web:/web:ro
```

**验证**：`ssh root@<ECS_IP> "grep -E '^(IMAGE|APP_PORT|COOKIE_SECURE)=' /opt/my-app/.env"` 输出正确。

### ⑥ 首次发布

```bash
bun run deploy
```

期望输出：

```text
▶ [后端] 1/4 运行测试
▶ [后端] 2/4 构建并推送 …（linux/amd64）
▶ [后端] 3/4 服务器拉取并重启
▶ [后端] 4/4 等待健康检查
✅ 后端发布完成
▶ [前端] 1/3 类型检查并构建
▶ [前端] 2/3 上传到 <ECS_IP>:/opt/my-app/web/releases/<版本>
▶ [前端] 3/3 切换版本
  后端还没托管前端，重启 app 容器      ← 只有第一次会出现，见坑 5
✅ 前端发布完成
```

**验证**（在服务器上，或者开了临时端口后从外网）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/health   # 200
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' http://127.0.0.1:3000/week   # 200，且很快
docker compose ps   # healthy
```

### ⑦ 创建账号

```bash
ssh -t root@<ECS_IP> "cd /opt/my-app && docker compose exec app bun run user:create <用户名>"
```

注意 `-t`：要分配终端，密码输入才能关闭回显（见坑 13）。

### ⑧ 绑定域名并上 HTTPS（Cloudflare + 1Panel）

1. **Cloudflare 加 A 记录**：`app` → `<ECS_IP>`，**Proxy status 关掉（灰云）**，和已有记录保持一致。
2. **1Panel → 网站 → 创建 → 反向代理**：主域名 `app.example.com`，代理地址 `http://127.0.0.1:3000`。
3. **1Panel → 证书 → 申请证书**：Acme 账户选 Let's Encrypt，**验证方式选 HTTP**，勾「自动续签」（为什么不用 DNS 验证，见坑 9）。
4. **站点 → HTTPS**：启用，HTTP 选项「自动跳转 HTTPS」，选刚申请的证书，保存。
5. **修反向代理配置**：把 `X-Forwarded-For` 从追加改成覆盖（见坑 10），`openresty -t` 后 reload。
6. **服务器 `.env` 改 `COOKIE_SECURE=true`**，`docker compose up -d`。
7. **关掉临时入口**：删除临时 HTTP 端口的代理配置，安全组里删掉对应规则。

**验证**：

```bash
curl -sI http://app.example.com/        # 301 → https
curl -sI https://app.example.com/       # 200，带 strict-transport-security
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://app.example.com/mcp   # 未带令牌应是 401
echo | openssl s_client -connect <ECS_IP>:443 -servername app.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -enddate
```

最后在浏览器里真正登录一次，确认安全 Cookie 下能登录、刷新后还在登录态。

## 前后端分开发布是怎么做的

原来是前端打进镜像、一起发布，只改一个按钮也要重建镜像、重启容器。拆开后：

| 命令 | 做什么 | 重启后端 |
|---|---|---|
| `bun run deploy:server` | 测试 → 构建镜像推 ACR → 服务器 pull + up → 等 `/api/health` | 是 |
| `bun run deploy:web` | 类型检查 → 构建 → tar 流式上传到 `web/releases/<版本>` → 原子切换 `current` | 否 |
| `bun run deploy` | 先后端再前端 | 是 |

先后端再前端的原因：接口有新增时，新页面上线那一刻接口已经就绪。

切换软链用「先建临时链接再 `mv -T` 覆盖」，`current` 任何时刻都存在：

```bash
cd /opt/my-app/web
ln -sfn releases/<新版本> current.tmp && mv -Tf current.tmp current
ls -1dt releases/* | tail -n +6 | xargs -r rm -rf   # 只保留最近 5 个版本
```

前端回滚就是把软链指回旧版本，立即生效：

```bash
cd /opt/my-app/web && ls -t releases
ln -sfn releases/<旧版本> current
```

上传没用 rsync，而是 `tar -czf - . | ssh … "tar -xzf - -C …"`，服务器上不用额外装东西。

CI 复用同一套脚本：GitHub Actions 里把密钥写成环境变量、把 SSH 私钥写到文件，然后按需要执行 `deploy.sh`、`deploy-server.sh` 或 `deploy-web.sh`。手动触发时可以选 `all / server / web`。

## 踩过的坑

### 坑 1：镜像构建报 `lockfile had changes, but lockfile is frozen`

- **现象**：`bun install --frozen-lockfile` 在 Docker 里失败，本地好好的。
- **原因**：仓库是 workspace（`apps/*`），后来新加了一个子包，Dockerfile 的依赖层只 COPY 了部分子包的 `package.json`。lockfile 按整个 workspace 校验，少一个就算「有变化」。
- **解决**：依赖层把 `apps/*` 下每个 `package.json` 都 COPY 进去。以后新增子包要记得同步改 Dockerfile。

### 坑 2：Apple Silicon 上构建 amd64 镜像，`bun install` 解压失败

- **原因**：在 QEMU 模拟的 amd64 环境里跑 `bun install` 不稳定。
- **解决**：安装依赖的阶段写成 `FROM --platform=$BUILDPLATFORM …`，在本机原生架构上装；纯 JS 依赖可以直接拷进目标架构的运行镜像。

### 坑 3：每次打开页面卡 12 秒，接口和 JS 却很快

- **现象**：经过反向代理访问 `/`、`/week` 都要 12 秒左右；直连 `127.0.0.1:3000` 是毫秒级；`/api/*` 和 JS 文件经过代理也很快。
- **定位**：绕过代理，用 `curl -0`（HTTP/1.0）直接请求后端，HTML 页面稳定 12 秒，HTTP/1.1 则是瞬间返回。
- **原因**：Nginx/OpenResty **默认用 HTTP/1.0 回源**。Bun 对 HTTP/1.0 请求返回 HTML（分块传输）时，要等到空闲超时才断开连接。
- **解决**：反向代理里加上

  ```nginx
  proxy_http_version 1.1;
  proxy_set_header Connection "";
  ```

  1Panel 创建反向代理站点的模板默认就带 `proxy_http_version 1.1`，手写的 Nginx 配置要自己加。

### 坑 4：静态目录用绝对路径时，前端路由全部 404

- **现象**：`WEB_DIST_DIR=/web/current` 时 `/` 正常，`/week` 这类前端路由 404；默认的相对路径一直没问题。
- **原因**：Hono 的 `serveStatic({ path })` 会把 `path` 拼到 `root`（默认 `./`）后面，绝对路径被当成了相对路径。
- **解决**：SPA 兜底写成 `serveStatic({ root: staticDir, path: 'index.html' })`，并补了一条「绝对路径也能兜底」的回归测试。

### 坑 5：第一次发前端，页面还是 404

- **原因**：后端启动时检查静态目录是否存在，不存在就不托管前端。第一次发布时先起了后端，那时 `web/current` 还没有。
- **解决**：前端发布脚本切完软链后，请求一次入口 JS；如果失败，就自动重启一次 app 容器再检查。只在第一次会触发。

### 坑 6：ACR 地址不是文档里常见的 `registry.<region>.aliyuncs.com`

- **现象**：照教程写了通用地址，推送时登录的却是另一个域名。
- **原因**：新开通的个人版实例有**专属域名** `crpi-<实例ID>.<region>.personal.cr.aliyuncs.com`，内网是在实例 ID 后面加 `-vpc`。
- **解决**：以控制台「访问凭证 → 登录实例」里给的域名为准。在 ECS 上 `getent hosts <vpc 域名>` 解析出来应该是 `100.x` 开头的内网地址。

### 坑 7：本机查 DNS 拿到 `198.18.x.x`

- **原因**：本机开着 Clash 之类的代理工具（fake-ip 模式），DNS 结果是假的。
- **解决**：验证解析时绕开本机 DNS，用 DoH 查：

  ```bash
  curl -s -H 'accept: application/dns-json' \
    "https://cloudflare-dns.com/dns-query?name=app.example.com&type=A" | jq '.Answer'
  ```

### 坑 8：本机 `curl` 测域名被 fake-ip 干扰

- **解决**：用 `--resolve` 把域名直接钉到服务器 IP，同时还能测 SNI 和证书：

  ```bash
  curl --resolve app.example.com:443:<ECS_IP> https://app.example.com/
  ```

### 坑 9：1Panel 申请证书卡在 `Wait for propagation`

- **现象**：用 Cloudflare DNS 账号验证，日志停在 `Wait for propagation [timeout: 30m0s]` 不动；可公网 DNS、权威 NS、服务器本机解析都已经能查到 TXT 记录。
- **再次尝试又报**：`An identical record already exists`。第一次申请创建的 TXT 记录还在，第二次申请想建同一条，被 Cloudflare 拒绝。
- **很可能的原因**：服务器访问 Let's Encrypt 接口**偶尔超时**。换成 HTTP 验证后，日志里明确出现了 `timeout awaiting response headers`；而 Let's Encrypt 那边，这次验证其实已经是 `valid`。DNS 那次一直停在本地传播检查，没留下更多日志，没法直接证实是同一原因。所以遇到卡住时，先按下面的排查手段确认 TXT 记录确实已经生效，再按网络超时处理。
- **解决**：
  1. 证书验证方式改成 **HTTP**（域名是灰云直连，1Panel 站点自带 `/.well-known/acme-challenge` 的 location，最省事）。
  2. 失败了**直接再点一次「申请」**：已通过的验证会被复用（日志里有 `authorization already valid; skipping challenge`），几秒就签发。
  3. 卡死的那条申请记录，以及它留在 Cloudflare 的 `_acme-challenge` TXT 记录，事后手动删掉。
- **排查手段**：

  ```bash
  tail -f /opt/1panel/log/ssl/<域名>-ssl-<ID>.log
  # 直接查 Let's Encrypt 那边的验证状态
  curl -s https://acme-v02.api.letsencrypt.org/acme/authz/<账号ID>/<授权ID> | head
  ```

### 坑 10：1Panel 反向代理默认的 `X-Forwarded-For` 能被伪造

- **原因**：1Panel 模板写的是 `$proxy_add_x_forwarded_for`，会把客户端自带的值保留下来，再在后面追加真实 IP。应用做登录限流时取的是**第一个** IP，客户端随便填一个就能绕过。
- **解决**：改成覆盖：

  ```nginx
  proxy_set_header X-Forwarded-For $remote_addr;
  ```

  配置在 `/opt/1panel/www/sites/<域名>/proxy/root.conf`。注意：在 1Panel 界面里改过这个站点的反向代理后，要再检查一遍这一行。开启 HTTPS 时 1Panel 会重新生成配置，这次手改的内容保留下来了。

### 坑 11：开了 `COOKIE_SECURE=true` 后，HTTP 入口登录不上

- **原因**：Secure Cookie 只会在 HTTPS 下回传。
- **解决**：先用 HTTP 临时入口验证时必须是 `false`；切到 HTTPS 后改成 `true`，同时关掉 HTTP 临时入口，避免出现「能打开却登不上」的入口。

### 坑 12：服务器上只有 1Panel 的 OpenResty，没有 `nginx` 命令

- **现象**：`nginx -v` 提示 command not found，`/etc/nginx` 也不存在，但 80/443 明明有服务在监听。
- **原因**：1Panel 的 OpenResty 跑在容器里（host 网络），配置映射在宿主机：
  - 站点配置：`/opt/1panel/www/conf.d/*.conf`
  - 站点目录：`/opt/1panel/www/sites/<域名>/`
- **操作方式**：

  ```bash
  docker exec <openresty 容器名> openresty -t           # 先检查
  docker exec <openresty 容器名> openresty -s reload    # 再重载
  ```

  改之前先备份，检查不通过就还原，别影响同机的其他站点。

### 坑 13：建账号时密码明文显示在终端

- **原因**：脚本用了 `prompt()` 读密码，它会回显输入。
- **解决**：读密码前 `stty -echo`，读完恢复；不是 TTY（比如管道输入）时跳过。`docker compose exec` 和 `ssh` 都要带 `-t`，才有 TTY。

### 坑 14：部署脚本里中文提示把变量名吞了

- **原因**：中文 locale 下，bash 会把紧跟在 `$VAR` 后面的全角字符当成变量名的一部分。
- **解决**：脚本里一律写 `${VAR}`。

### 坑 15：一些平台上的小坑

- **macOS 的 `mv` 没有 `-T`**：软链原子切换只能在 Linux 服务器上执行，本地模拟要用 `ln -sfn`。
- **1Panel 开了安全入口**：直接访问面板端口会显示「Access Temporarily Unavailable」，要在服务器上执行 `1pctl user-info` 查入口路径（它会同时显示用户信息，别贴到聊天记录里）。
- **`gh` 报 401**：shell 里遗留的 `GH_TOKEN` 环境变量覆盖了 keyring 里的有效登录，去掉这个变量就好。
- **安全组放行公网端口**：属于降低安全性的操作，自动化工具通常会要求人工确认，预留这一步的时间。
- **2G 内存、没有 swap**：同机跑了多个服务时，可用内存只剩 500M 左右。出现 OOM 或卡顿时，优先考虑加 swap。

## 小结

这次上线最费时间的不是「怎么部署」，而是三类细节：

1. **代理层的默认值**：HTTP/1.0 回源、`X-Forwarded-For` 追加。它们不报错，只表现为「慢」或「不安全」。
2. **平台的隐含约定**：ACR 专属域名、1Panel 的配置路径和安全入口、1Panel 证书申请的重试行为。
3. **首次运行才会出现的状态**：前端目录还不存在、lockfile 校验不过、Secure Cookie 在 HTTP 下失效。

把这些写进脚本的自检和文档的验证步骤之后，日常发布就只剩一条命令了。
