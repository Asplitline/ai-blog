## 为什么收藏

这篇文章将 Lauren Tan（@poteto）的演讲、访谈、长文和推文整理为一套可操作的 Agent 团队工作方法：从教会一个 Bot 完成任务，到通过技能、验证、例行任务和反馈循环实现可靠交付。对设计 Agent 平台、定时任务与开发工作流尤其有参考价值。

以下是阅读笔记与实践提炼；完整内容请阅读原文。

## 核心观点

1. **信任先于规模。** 先建立单个 Bot 的稳定交付能力，再按职责和上下文边界拆分角色。团队规模取决于验收和协调能力。
2. **让 Bot 理解目标与上下文。** 提供业务背景、完成标准与必要权限，让它复述任务理解，减少执行中的反复纠偏。
3. **建立四阶段信任阶梯。** 人工观察执行 → 将成功步骤固化为 Skill → 只给任务名独立验证 → 设置定时或事件触发的例行任务。
4. **明确职责与权限。** 每个 Bot 应有清晰的工作范围、可调用工具、禁区和审批规则；涉及付款、公开发布、对外沟通时保留人工确认。
5. **团队协作需要共同状态。** 协调者负责分派，专业 Bot 负责交付；任务状态、交接摘要、证据与待决问题应可追踪。
6. **例行任务控制成本。** 用事件过滤、适当频率、专用上下文与脚本化步骤减少无效唤醒。
7. **每个环节都要提供验收证据。** 测试、截图、操作录屏和可追溯链接比口头宣称完成更可靠；每个阶段都应有暂停或升级条件。
8. **重复错误优先改系统。** 优先调整结构与自动检查，然后沉淀 Skill，最后辅以人工抽查。
9. **工程 Agent 先构建验证工具。** 支持启动项目、操作页面、读取结果并保留录屏，让 coding agent 具备端到端验证能力。

## 可复用的工作流

```text
外部事件 / 定时触发
        ↓
收集与过滤上下文
        ↓
协调 Agent 进行任务分派
        ↓
执行 Agent + Skills + Tools
        ↓
测试 / 截图 / 日志 / 事实核查
        ↓
人工审批（需要时）
        ↓
提交 / 发布 / 通知
        ↓
记录错误、更新技能和验收规则
```

## 从原文中提取的高价值实践

以下按「操作方法 → 可复制指令 → 验收标准」整理。**引号中的中文提示词是便于实际使用的改写或用户摘录，除明确标注外，并非逐字引用原作者。**内容依据 [Kyle_13 原文入口](https://x.com/i/article/2117212639658954752)、[SOTA Sync 的分章梳理](https://sotasync.com/reader/2026-11-03-lauren-tan-grok-bot-methodology/)及相关 [Lauren Tan 指南资料索引](https://github.com/sit-in/awesome-grokbot-playbooks/blob/main/docs/x-articles.md) 提炼。

### 1. 对话结束前，让 Bot 复述它理解的任务

**要点：先检验理解，再开始执行。** 先讲清业务背景、期望结果和顾虑，尤其适合用语音把尚未整理好的想法说出来。随后让 Bot 复述目标、约束与仍有疑问的地方，纠正偏差后再授权。

**可复制的话术：**

> 用你自己的话复述一遍，让我确认你听懂了。

复杂任务可以扩展为：

> 开始执行前，复述你的任务目标、关键约束、成功标准和仍需确认的问题。等我确认理解一致，再开始操作。

**验收：** Bot 能准确讲出要交付什么、不能做什么，以及哪些决定要交还给人；遇到有歧义的前提主动提问。

### 2. 做设计：先收集优秀案例，再制作 Mood Board

**要点：先对齐审美与方向，再制作页面。** 在落地页、产品界面或品牌视觉工作中，先让 Bot 搜索优质案例，整理其排版、色彩、字体、留白、叙事节奏与交互方式，形成情绪板（Mood Board），给出几条明确的视觉路线，再由人选择一条进入制作。

**可复制的话术：**

> 先找 8–12 个优秀的同类落地页案例，附原始链接和截图。按字体、色彩、网格、插画或摄影、交互和信息层级整理成 Mood Board。基于这些参考给我 3 个差异清晰的设计方向，解释各自适合的用户与场景。等我选定方向后，再做页面原型。

**验收：** 有可追溯参考、有可比较的方向、有选择理由，最终原型能对应所选情绪板。这里的「8–12 个」「3 个」是实践建议，非原作者的固定数字。

### 3. 每完成一条成熟流程，就让 Bot 把它写成 Skill

**要点：把反复有效的操作变成可用名称调用的能力。** 一次任务做对后，立即整理输入、执行步骤、质量标准、异常处理及需要人确认的操作，存进 Skill；之后只说名称即可复用。团队可以把稳定技能维护在独立的私有代码仓库，并定期清理过时步骤。

**可复制的话术：**

> 把我们刚才的做法写成一个技能，名字叫【xxx】，以后我说这个名字你就照做。

更适合工程落地的版本：

> 把刚才验证通过的步骤写成 Skill「xxx」：包含适用场景、触发词、输入、操作顺序、交付物、验收标准、失败处理和需人工批准的动作。保存后列出三个测试样例，下一次只通过技能名称调用。

**验收：** 换一个会话、只提供任务名及必要输入，Bot 仍能稳定完成；遇到异常能停止并说明原因。先验证再沉淀，Skill 才有可靠的依据。

### 4. 用「看它做 → 教它做 → 一次做对 → 自主执行」建立信任

**要点：授权随稳定性逐级增加。**

1. **先看它做：** 第一次让 Bot 处理真实任务，完整观察操作，记录遗漏、错误及需要补充的背景。
2. **再教它做：** 人工纠正，明确标准，把验证成功的流程写成 Skill。
3. **确认能一次做对：** 下一次只给任务名称与必要参数，不再边做边提醒；使用明确的验收清单检查产物。
4. **最后让它自己做：** 达标后接入定时任务或事件触发，保留日志、失败通知和必要审批。

**案例：** 邮件收据整理可先由人观察分类、核对字段，再把规则写进 Skill，单独验证一次，最后才让新邮件自动触发。订票或付款可自动完成比价与材料准备，交易前保留人的确认。

**验收：** 重复执行的结果一致，敏感操作能正确暂停，失败时能回报证据和下一步建议。

### 5. 一个 Bot 一件事、一种表达方式、一组明确禁区

**要点：少而精，先明确责任再扩编。** 一个 Bot 有清晰、长期稳定的岗位；定义它要负责的任务、沟通语气和输出形式、必要工具，以及绝对不能自行处理的行为。Lauren Tan 提及使用 **Dr Eggbot** 作为 Bot 设计师，帮助创建与调整角色。

**可复制的话术：**

> 帮我设计一个只负责【任务】的 Bot。它的输出风格是【风格】，必须交付【产物】，可以使用【工具】；禁止【越权行为】。遇到【异常条件】必须停下并向我报告。先指出职责中模糊或冲突的地方，再给出最终岗位说明。

示例角色表：

| Bot | 只负责 | 交付物 | 禁止事项 |
| --- | --- | --- | --- |
| 情报 Bot | 按来源收集与核验 AI 资讯 | 带出处的候选清单 | 编造来源、擅自发布 |
| 编辑 Bot | 将已确认材料整理为 MDX | 草稿与来源清单 | 擅自更改事实、直接合并 |
| 验收 Bot | 检查链接、格式、证据和构建 | 审查结果 | 绕过检查、替人批准 |

**验收：** 把跨职责任务交给其中一个 Bot，它会转交或请求协调，而非擅自扩张工作范围。只有出现稳定的专业分工需求时再增设角色。

### 6. 像带新员工一样，为 Bot 做入职培训

**要点：提供工作的来龙去脉，而不是只给一条命令。** 介绍你是谁、目标是什么、日常工作流、常用工具、术语、口味与质量底线；让 Bot 复述并提出自动化候选，按节省的重复劳动优先级排序。必要账号与授权使用专门工具和保险库管理，权限按任务范围分配。

**可复制的话术：**

> 这是我的工作背景、目标、常用工具与交付标准。请先复述理解，再列出我每周需要重复完成的工作，按频率、耗时、风险和自动化价值排序；挑出最适合从一个小任务开始训练的项目。

**验收：** 它能用业务语言解释优先级，并指出缺少的上下文和权限。

### 7. 多 Bot 团队：一个协调入口，多个专业角色，共享明确状态

**要点：由协调 Bot 接任务、分派、追踪、汇报。** 专业 Bot 保留各自职责与偏好；项目状态与交接材料放在共同可访问的位置，交接写清当前进度、已验证成果、阻塞项和下一步。只在完成、需要审批或出现异常时主动通知，减少噪声。

**可复制的话术：**

> 你是任务协调者。先识别目标、完成标准和需要哪个专业 Bot，再分派任务。每次交接附任务链接、当前状态、证据、阻塞问题与下一负责人。只有完成、失败或需要我决策时才通知我。

**验收：** 多个角色之间能追踪同一任务，无需人肉复制上下文；每个任务有唯一负责人及可追溯状态。

### 8. Routine：经过验证的任务，才值得定时运行

**要点：按时间或事件触发都应控制唤醒成本。** 可先用便宜的规则或脚本判断「有没有变化」，有价值才唤醒 Agent；将长期机械操作改成脚本，让专职 Bot 使用干净的任务上下文。原文讨论过每小时一次或一天数次作为通常足够的频率，也有工作时段每三十分钟检查的特定例子；调度频率应由任务时效性决定。

**可复制的话术：**

> 把【已验收任务】改成 Routine。先说明触发条件、预计频率、无变化时如何跳过、每次读取哪些最小上下文、失败重试方式、成本上限与人工审批点。先试运行并展示样例输出，再启用计划。

**验收：** 无变化时少消耗资源，异常有明确日志，任务可暂停和重试。

### 9. 交付必须有证据，每个阶段都能叫停

**要点：以可复现的交付物代替口头的「完成了」。** 编程任务应提供测试结果、修改文件、前后截图或录屏、相关 PR 与构建状态；资料任务应附原始出处和未证实信息；对外发送、花钱、发布等动作明确人工审批。原文提及一套 Slack 反馈 → Linear 工单 → Agent 复现与修复 → 独立验证的流程，并在该场景保留一小时人工否决窗口。这是具体案例，不能直接当作普遍自动发布规则。

**可复制的话术：**

> 完成后输出证据包：任务目标、已执行操作、生成产物、验证步骤与结果、原始链接、残余风险以及需要我批准的事项。证据不足时标记未通过，并说明卡在哪一步。

**验收：** 审核者可以独立复核；不确定项有标记；审批关口有效。

### 10. 重复犯错：优先改环境，再改 Skill

**要点：重复纠错应形成系统性改进。** 原文思路可归为：调整结构让正确操作更容易 → 增加自动检查拦错 → 更新技能步骤 → 人工抽查。比如总是漏掉 MDX 字段，就把必填检查写进脚本；总是抓错日期，就固定权威数据源；常见错误集中记录后定期找共因。

**可复制的话术：**

> 回顾最近的失败和人工纠正，按共同根因分组。优先提出目录、模板、工具或校验规则的改进，再更新相关 Skill。每项改进给一个自动化回归测试，避免下次重复犯错。

**验收：** 相同类型问题在下次执行时被结构、自动化校验或技能规则提前拦截。

## 一套可以直接应用到 AI 学习周报的演练

以「每周五整理 GitHub AI Trending 并生成博客 Draft PR」为例：

1. **先对齐：** 要求 Bot 复述时间窗口、筛选标准、目标读者、MDX 格式与 PR 审核要求。
2. **人工示范：** 先运行一期，检查项目来源、重复项目、学习价值与推荐理由。
3. **沉淀 Skill：** 命名为「AI 周报」，包含筛选、分类、原始链接、评分依据、文章检查与异常处理。
4. **一次性验证：** 新会话只说「执行 AI 周报」，检查是否独立遵循所有规则。
5. **启用 Routine：** 周五运行、自动建 Draft PR；合并动作由人审批；失败时带证据通知。
6. **每周回顾：** 收集遗漏、误判、坏链接以及 PR 审查意见，优先改检查器与 Skill。

这段是针对本博客工作流的**应用示例**，并非原作者的具体案例。

## 对 Agent 产品开发的启发

### 1. 定时任务的启用流程

把「创建定时任务」拆成可审核阶段：

- 首次在对话里运行，用户观察与纠错。
- 提炼为可复用 Skill，写清输入、输出、边界与异常处理。
- 复跑一次，使用明确验收标准检查结果。
- 再创建 Schedule / Event Trigger，并提供暂停、日志与失败通知。

### 2. 任务结果卡片

每次 Agent 交付建议展示：

- **任务与触发来源**：为什么运行、输入来自哪里。
- **步骤与产物**：已执行哪些操作、生成哪些文件或 PR。
- **验证证据**：测试结果、截图、日志、引用链接。
- **决策入口**：批准、拒绝、重试、人工接管。
- **经验沉淀**：本次纠错是否更新 Skill 或自动检查。

### 3. Multi-Agent 的扩展原则

从主 Agent 与一个执行 Agent 开始；当职责、权限或上下文确实需要隔离时，再引入专业角色。协调层负责路由与汇总，共享任务状态负责协作，独立验证负责质量。

## 阅读后实践

- [ ] 选一个每周重复的工作流（例如 AI 学习资料收集），记录完整的手动操作。
- [ ] 先让一个 Agent 完成并人工验收。
- [ ] 将步骤、输入、验收标准和异常处理整理成 Skill。
- [ ] 复跑验证后配置定时任务。
- [ ] 为结果增加来源链接、执行日志、异常情况和审批入口。
- [ ] 一周后回顾失败案例，优先优化流程与自动检查。
